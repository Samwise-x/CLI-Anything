# Research: GitHub governance for autonomous repository work

**Research date:** 2026-10-15
**Scope:** First-party documentation and upstream project documentation only. This note informs repository configuration; it does not assert the current repository account plan or settings have been inspected.

## Recommended control model

Treat autonomous execution as a proposal-producing worker. Keep planning, code execution, evaluation, and privileged merge/release actions in distinct workflows/jobs with separate permissions and runners. The independent evaluator should consume the proposed diff and immutable test/evidence outputs, and produce a named required status check. Only GitHub-side rulesets/branch protection can make the required checks and review policy a merge gate. A local loop, pre-commit hook, PR comment, or agent instruction is not the enforcement boundary.

This separation is a design recommendation inferred from GitHub's documented token, event, and runner trust boundaries below. It is not an assurance that any particular agent loop is safe by itself.

## Workflows, event permissions, and fork PRs

- Declare a restrictive workflow-level `permissions` map, then grant the smallest extra permission at the job that needs it. If a workflow declares any permission, unspecified permissions become `none`; GitHub also recommends minimum permissions and pinning third-party actions to full commit SHAs. [Workflow permissions](https://docs.github.com/en/actions/how-tos/writing-workflows/choosing-what-your-workflow-does/controlling-permissions-for-github_token), [GitHub Actions security hardening](https://docs.github.com/en/code-security/tutorials/secure-your-organization/protect-against-threats)
- Run untrusted fork code only under `pull_request` with read-only `GITHUB_TOKEN` and no repository secrets. Never check out or execute fork-controlled code in `pull_request_target`; that event runs with base-repository secrets and a privileged token. For privileged labeling/triage, use `pull_request_target` only against trusted base-branch code and pass sanitized metadata, without checking out or executing the PR contents. [Securely using `pull_request_target`](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target), [fork workflow settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository)
- Treat `workflow_run` as privileged: the downstream run can receive secrets and write tokens even if the upstream run did not. Do not execute files/artifacts from an untrusted PR in that downstream context. Bind artifacts to a trusted run/commit and validate their origin/content before any privileged action. [Workflow events: `workflow_run`](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)
- Avoid path/branch/commit-message skipping on checks that are required: GitHub documents skipped workflows can leave required checks pending and block merges. Use an always-triggered required workflow with conditional jobs and an explicit final gate job, or choose required check names that cannot be skipped. If using merge queues, required Actions checks must also listen to `merge_group`. [Skipping workflow runs](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/skip-workflow-runs), [required status check troubleshooting](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)
- `schedule` runs only from the default branch; public repository scheduled workflows are disabled after 60 days without repository activity. Make long-running orchestration resumable/idempotent and use `workflow_dispatch` or another event as a recovery trigger. [Workflow events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)

## Runners and isolation

- GitHub explicitly warns that self-hosted runners are not guaranteed to use ephemeral clean VMs and can be persistently compromised by untrusted workflow code. GitHub says self-hosted runners should almost never be used for public repositories. Do not attach a workstation, WSL host, secret-bearing server, or persistent runner to untrusted PR execution. [Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use)
- Prefer GitHub-hosted standard Linux runners for public PR CI: their usage is free for public repositories. Self-hosted runner usage has no Actions runner charge, but the operator still owns hardware, isolation, patching, logs, and incident response. Cost-free is not risk-free. [Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)
- If self-hosted runners are required for trusted jobs, dedicate a runner group to the repository and job class, restrict repository access, keep it off fork-triggered workflows, and use disposable/ephemeral execution environments with no route to sensitive networks. GitHub’s own security guidance requires checking isolation and non-reuse for privileged PR automation. [Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use), [runner groups](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/manage-access)

## Main-branch protection, checks, reviews, and auto-merge

- For a public repository on GitHub Free, repository rulesets and protected branches are available. A ruleset can require a PR, required status checks, reviews, code-owner review, resolved threads, and block force pushes/deletion. Rulesets enforce server-side policy; commit these settings as an administrator-managed control and verify the effective ruleset after applying it. [Rulesets availability and rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets), [rulesets overview](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)
- Required check names must correspond to checks that actually run and report on every applicable PR. Do not require a path-filtered or otherwise skipped workflow; ensure it has a successful report on the latest commit SHA. GitHub notes checks may be restricted to a specific expected GitHub App source. [Available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets), [required status check troubleshooting](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)
- Auto-merge is available for public repositories on GitHub Free. It waits for required reviews and checks, then merges; it does not define those requirements. Enable it only after branch rules require independent validation and any human/code-owner review policy intended by the project. A new push by a non-writer or base-branch change can disable auto-merge. [Automatically merging a pull request](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/automatically-merging-a-pull-request)
- `CODEOWNERS` works in public GitHub Free repositories and requests review automatically when owned files change. The file must exist on the PR base branch; owners need write access. A repository admin must separately enable the “require review from Code Owners” rule for it to gate merging. [About code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)
- A required workflow/required-check rule and auto-merge must never allow the autonomous worker to approve its own changes or modify the policy files that govern its own merge path without an independent trusted review. This is governance guidance derived from the documented ability to configure permissions/rules and the purpose of review gates.

## Security tools and plan boundaries

- Dependabot alerts are available for public, private, and internal repos and can be enabled by repository admins. Dependabot security updates create PRs for known vulnerable dependencies; version updates can keep dependencies current through `.github/dependabot.yml`. Do not treat Dependabot PRs as automatically safe to merge: route them through the same required checks and review policy. [Dependabot alerts](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/secure-your-dependencies/configure-dependabot-alerts), [Dependabot quickstart](https://docs.github.com/en/code-security/tutorials/secure-your-dependencies/dependabot-quickstart)
- Public repositories have free code scanning, secret scanning, dependency review, and Dependabot alerts. Secret scanning is automatic for public repositories. Repository-level secret scanning push protection requires Secret Protection, but GitHub separately provides account-level user push protection for public repositories; do not assume repository-level push protection is enabled. Code scanning and paid Advanced Security features on private repositories may require GitHub Code Security/Secret Protection. [Advanced Security availability](https://docs.github.com/en/get-started/learning-about-github/about-github-advanced-security), [secret scanning scope](https://docs.github.com/en/code-security/reference/secret-security/secret-scanning-scope), [push protection](https://docs.github.com/en/code-security/concepts/secret-security/push-protection)
- GitHub Actions standard-hosted runner use is free for public repositories, and self-hosted runner execution is not billed by GitHub. Private repositories receive plan-dependent minutes/storage and may incur charges above allowance. [Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)
- OIDC is useful only where a workflow needs a third-party cloud/registry credential: it exchanges a short-lived GitHub identity token for provider credentials rather than storing a long-lived cloud secret. Keep `id-token: write` scoped to the specific job and constrain the cloud trust policy to repository/ref/environment claims. `id-token: write` itself permits requesting a token; cloud-side trust policy determines what it can access. For a local-only project with no external deployment target, no OIDC setup is needed. [OIDC concepts](https://docs.github.com/en/actions/concepts/security/openid-connect), [OIDC cloud-provider configuration](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-cloud-providers)

## Hooks, linters, and CI parity

- Keep fast deterministic checks in a local pre-commit hook for feedback, and run the same checks in GitHub Actions as the authoritative merge gate. Git hooks can be bypassed with `git commit --no-verify`, so local hooks cannot replace server-side required checks. [Git hooks](https://git-scm.com/docs/githooks), [pre-commit framework](https://pre-commit.com/)
- Use actionlint to statically validate workflow syntax, expressions, action inputs/outputs, permissions, likely injection issues, and related workflow mistakes; it can run locally or in CI and has a documented pre-commit integration. Pin the hook version. [actionlint README](https://github.com/rhysd/actionlint/blob/main/README.md), [actionlint checks](https://github.com/rhysd/actionlint/blob/main/docs/checks.md), [actionlint pre-commit integration](https://github.com/rhysd/actionlint/blob/main/docs/usage.md#pre-commit)
- Run policy-as-code checks over the workflow and repository governance files, plus tests for the autonomous loop’s state transitions, cancellation/resume, budget limits, retry/self-healing boundaries, evidence provenance, and evaluator independence. Make planning, execution, test/evaluation, and release/merge separate capabilities; grant write permissions only to the final trusted job. This is a recommended architecture, not a feature GitHub provides automatically.

## Practical sequence for this repository

1. Inventory current workflows, actions, scripts, triggers, and required check names; establish the project test command and a CI-equivalent local command.
2. Create CI with read-only defaults, fork-safe PR validation, pinned actions, Linux hosted runners, actionlint, repository linters/tests, and an always-reported aggregate gate.
3. Configure a public-repository ruleset for `main`: PR required, all designated checks required, no force push/deletion, and review/code-owner requirements appropriate to the maintainer model. Protect workflow, policy, and evaluator files with CODEOWNERS and require their approval.
4. Add issue/PR automation only with narrow event-specific permissions. Keep triage/comment automation separate from CI and from trusted release permissions.
5. Add Dependabot manifests and security updates; enable code scanning and secret scanning in repository settings if available for the repository’s visibility/plan. Track which features are repository settings versus versioned files.
6. Add auto-merge only after the previous gates are verified. Allow autonomous work to open/update a draft PR and provide evidence; final merge remains governed by required checks and independent approval policy.
7. For long-running loops, use durable state/evidence artifacts, job concurrency and cancellation semantics, bounded retries/budgets, and restartable dispatch; do not rely on one indefinitely running Actions job. Confirm implementation details against current Actions limits before choosing specific durations.
