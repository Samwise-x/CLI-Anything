# NotebookLM harness: WSL install and auth feasibility

Research date: 2026-10-15. Scope: public upstream documentation/package metadata and the local CLI-Anything wrapper. No package was installed; no browser, Google account, or credential state was accessed.

## Recommendation

Install `notebooklm-py[browser]` into the harness's existing isolated WSL virtual environment (not the system interpreter), then ensure that environment's `bin` directory is on the wrapper process `PATH`. Upstream says Python 3.10+ is supported; on Debian/Ubuntu, `pip` in a virtual environment is supported, while an isolated CLI installer (`uv tool install` or `pipx install`) is preferred when installing outside a project environment. The `[browser]` extra is needed for interactive browser login; ordinary API/CLI calls with already supplied auth need only the base package. [Upstream install guide](https://github.com/teng-lin/notebooklm-py/blob/main/docs/installation.md#quick-install-tldr-by-persona)  |  [PyPI metadata](https://pypi.org/project/notebooklm-py/)

The current harness README's `python3 -m pip install --user 'notebooklm-py[browser]'` is less suitable for this WSL setup: upstream's current Linux guidance warns that system Python may reject installs under PEP 668 and directs users to an active virtual environment or isolated installer. [Local harness README](../notebooklm/agent-harness/cli_anything/notebooklm/README.md)  |  [Upstream install guide](https://github.com/teng-lin/notebooklm-py/blob/main/docs/installation.md#quick-install-tldr-by-persona)

## Authentication paths and Windows boundary

- **User-controlled browser flow:** `notebooklm login` is upstream's primary login route. WSL is a documented exception: the browser opens on the Windows host, while `storage_state.json` is saved in the WSL filesystem. Thus it does not install the CLI or place its auth file on Windows, but it does use Windows-host browser UI. If "nothing on Windows" excludes even browser UI, this path is blocked by that constraint; otherwise it is the supported route and the user should complete/sign off the browser interaction. [Upstream installation](https://github.com/teng-lin/notebooklm-py/blob/main/docs/installation.md#platform-notes)  |  [Upstream configuration: WSL](https://github.com/teng-lin/notebooklm-py/blob/main/docs/configuration.md#platform-notes)
- **Non-interactive route:** upstream supports a pre-existing `storage_state.json`, `--storage PATH`, or `NOTEBOOKLM_AUTH_JSON` environment variable. These avoid browser login on the WSL machine, but the secret still must be provisioned into WSL from an authorized secret source. They are not a way to use a logged-in browser session without moving/provisioning auth material. No such credential was read or moved for this research. For this task, do not copy the Windows browser profile or export its cookies. [Installation: headless/CI](https://github.com/teng-lin/notebooklm-py/blob/main/docs/installation.md#d-headless-server-or-ci)  |  [Configuration: NOTEBOOKLM_AUTH_JSON](https://github.com/teng-lin/notebooklm-py/blob/main/docs/configuration.md#notebooklm_auth_json)
- **Browser cookie extraction:** optional `[cookies]` plus `notebooklm login --browser-cookies ...` imports cookies from a supported browser profile. It requires access to that browser's local profile; it is not the zero-transfer solution for this environment and should not be used against the Windows profile under the no-Windows constraint. [Upstream install guide: extras](https://github.com/teng-lin/notebooklm-py/blob/main/docs/installation.md#optional-extras-matrix)
- **Avoid master-token auth for this test:** upstream documents `master_token.json` as durable, account-equivalent, broader-blast-radius credential. It is unnecessary for short-lived harness validation. [Upstream installation: master-token warning](https://github.com/teng-lin/notebooklm-py/blob/main/docs/installation.md#alternative-master-token-auth-no-cookie-file-to-ship-survives-expiry)

## Files and permissions

By default, upstream stores state under `~/.notebooklm/profiles/<profile>/`: `storage_state.json` (Google session cookies), `context.json` (selected notebook/conversation), and `browser_profile/` (persistent Chromium user data); `config.json` is at `~/.notebooklm/`. `NOTEBOOKLM_HOME` relocates this tree and `NOTEBOOKLM_PROFILE` selects a profile. On this WSL account the default root would resolve under the Linux home directory, not the Windows profile. The cookie file is a bearer credential; upstream's security policy prescribes POSIX mode `0600` for it, `0600` for context/credential files, and `0700` for the browser profile. Do not put this tree in the repository, task outputs, or public archive. [Upstream configuration](https://github.com/teng-lin/notebooklm-py/blob/main/docs/configuration.md#file-locations)  |  [Upstream security policy](https://github.com/teng-lin/notebooklm-py/security)

For a later isolated probe, set `NOTEBOOKLM_HOME` to a fresh WSL-only temporary directory before invoking auth diagnostics. `notebooklm auth check --test --passive` is expressly read-only: it does not run refresh commands, rotate cookies, or write credentials. A probe with no auth state can verify local failure/diagnostic behavior without using any account credential; it cannot prove authenticated NotebookLM access. [Upstream CLI reference](https://github.com/teng-lin/notebooklm-py/blob/main/docs/cli-reference.md#authentication-auth-check)

## What can be exercised safely now

- **Feasible without installing notebooklm-py or accessing auth:** run harness unit tests with a fake `notebooklm` executable/subprocess; verify generated argv, JSON gating, explicit notebook IDs, timeout/nonzero-exit handling, error redaction, local session behavior, `--help`, and version output. The wrapper delegates subprocess execution and does not implement Google's API itself. [Local backend](../notebooklm/agent-harness/cli_anything/notebooklm/utils/notebooklm_backend.py)
- **Feasible after an isolated WSL install, still no account auth:** `notebooklm --help`, `--version`, harness command-help/smoke tests, and an auth diagnostic under a fresh `NOTEBOOKLM_HOME`. A passive auth check with no secret can confirm error-path behavior only.
- **Blocked until an auth path is explicitly enabled:** list/create notebooks, read sources/chat, artifact operations, and live service acceptance. These use Google NotebookLM and need valid auth. `auth check --test --passive` with valid auth can perform a read-only token-fetch check, but auth state must already exist in WSL. [Upstream CLI reference](https://github.com/teng-lin/notebooklm-py/blob/main/docs/cli-reference.md#authentication-auth-check)
- **Blocked under a strict no-Windows-UI rule:** interactive WSL login, because upstream intentionally opens the Windows host browser. No CLI-only non-interactive flow can conjure an authenticated session absent auth material already provisioned inside WSL.
